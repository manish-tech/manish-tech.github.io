From 10K to 100K+ rows: streaming Excel exports at constant memory

Oct 2026 · 6 min read

Retailers on our platform export their product catalogs to Excel all the time, for bulk edits, audits, and sharing with marketplaces. For a long time the export had an unofficial limit: around 10,000 rows. Beyond that, requests timed out or the service ran out of heap, and we'd tell the customer to split the export.

That doesn't work for a retailer with a six-figure catalog. This post covers the three changes that let the same service export 100K+ rows with flat memory usage.

Why it broke: the whole workbook lived in memory

The original code was the version you write first, and it's correct for small files:

Workbook wb = new XSSFWorkbook();
Sheet sheet = wb.createSheet("Products");
List<Product> products = repository.findAllByTenant(tenantId); // everything, at once
for (Product p : products) {
    Row row = sheet.createRow(rowIdx++);
    // ... populate cells
}
wb.write(response.getOutputStream());

It has two problems, and both grow linearly with catalog size:

  1. All the data is loaded up front. Every product document is in a List before the first row is written.
  2. XSSFWorkbook keeps the full XML tree in memory. Each cell is an object, and each object has overhead. An in-memory .xlsx takes up many times its size on disk.

It also ran synchronously inside an HTTP request, so even when memory held, the request timeout didn't.

Fix 1: stream the workbook with SXSSF

Apache POI ships a streaming variant, SXSSFWorkbook. It keeps a sliding window of rows in memory and flushes older rows to a temporary file as you go. Memory now depends on the window size, not on how many rows you write. 

SXSSFWorkbook wb = new SXSSFWorkbook(100); // keep only 100 rows in memory
wb.setCompressTempFiles(true);
try {
    Sheet sheet = wb.createSheet("Products");
    // ... write rows ...
    wb.write(out);
} finally {
    wb.dispose(); // delete the temp files, or they pile up on disk
    wb.close();
}

A few things to know:

  • Write only, forward only. Once a row is flushed you can't go back to it. Anything like column widths or summary rows has to be planned before you start writing.
  • Avoid autoSizeColumn. It needs every row in memory and defeats the point. Set fixed widths instead.
  • Always call dispose(). Temp files are written to disk, and forgetting to clean them up turns a memory problem into a disk problem.

Imports have the same problem in reverse. A .xlsx upload parsed with XSSFWorkbook loads everything into memory. For large uploads, POI's event-based SAX reader (XSSFReader with a sheet handler) gives you one row at a time.

Fix 2: read the data in pages

A streaming writer doesn't help if you still load the whole catalog first. We changed the Couchbase N1QL reads to fetch fixed-size pages and write each page to the sheet before fetching the next one. At any moment, memory holds one page of documents plus the SXSSF window. 

String cursor = null;
do {
    Page<Product> page = productRepository.fetchPage(tenantId, cursor, PAGE_SIZE);
    for (Product p : page.items()) {
        writeRow(sheet, p);
    }
    cursor = page.nextCursor();
} while (cursor != null);

We used keyset (cursor) pagination instead of OFFSET. With an offset, every page gets slower as you go deeper, because the database still has to scan and skip all the earlier rows. A cursor on an indexed field keeps page 1,000 as cheap as page 1. The same change helped cut our P99 query latency from over 2s to under a second.

Fix 3: take it off the request path with Kafka

Even when it's efficient, a 100K-row export takes longer than you'd want an HTTP request to stay open. So the export became a job:

  1. The API validates the request, publishes an export event to Kafka, and returns a job ID right away.
  2. A consumer picks up the event, runs the paginated, streaming export, and uploads the finished file to S3 in batches.
  3. The client polls the job status, or gets notified, and downloads the file when it's ready.

This also brought some side benefits:

  • Backpressure for free. A burst of exports queues up on the topic instead of overloading the service.
  • Retries. A failed export can be retried without the user doing anything.
  • Isolation. One tenant's huge export no longer slows down other tenants' API calls.

Takeaways

  • Look for anything that loads "all" of something. findAll, building the whole document in memory, and collecting results into a list all work in dev and break in production.
  • Streaming has to work end to end. A streaming writer fed by a non-streaming reader is still a non-streaming system.
  • Long-running work belongs in a job, not a request. Once something can take more than a few seconds, make it asynchronous.
